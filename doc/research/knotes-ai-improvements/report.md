# Knotes can catch up with the leaders through local search by meaning

*Written on 2026-11-14 from the notes in this folder. Since then, items 1 (the date and vault overview moved into a message frozen per conversation, `cached_tokens` logged) and 5 (the "not for AI" exclusions) have been built; see ADR 0027. Measurements on the Sign in with ChatGPT route showed that it caches at most the shared start of a request, so the history is kept unchanged only when the cache covers at least half of it. Item 6 (Snowball for Ukrainian) was tried and changed nothing in the search benchmark: under prefix search its stems do not join word forms any better than the current cut, so the gain needs stemming on the index side.*

The biggest gap in Knotes' AI is search, not the model and not the agent loop. On keyword queries Recall@5 is 0.97, but on queries "by meaning" it is 0 out of 9. Meanwhile, every serious notes harness of 2026 (qmd, Basic Memory, Obsidian Copilot with Miyo, Smart Connections) keeps a semantic layer, and Cursor measured **+12.5% accuracy from adding semantic search to grep** ([Cursor](https://cursor.com/blog/semsearch)). This gap can be closed locally, within the memory budget. That takes the EmbeddingGemma model (**<200 MB when quantized**, over 100 languages), int8 vectors with 256 dimensions (~51 MB for 200k blocks), brute-force search in memory, and result fusion that does not let semantics push out exact matches. The second layer is cheap changes with a big payoff. The first of them is a stable prefix for the OpenAI cache. Right now the date and the vault overview with exact counts sit in `instructions` and reset the cache for the whole conversation every time a note appears or disappears or tags change, even though cached input in plan credits costs 1/10–1/20 of regular input. Next come the Snowball stemmer for Ukrainian instead of chopping off letters, listing tools (queries by properties, dates in tasks, `since/until`) and a "completeness contract" in the prompt against stopping early and giving estimates instead of data. The third layer is trust: the "not for AI" boundary in the tool layer (decided in ADR 0004 but still not built), local citation checking, and injection hygiene for the chat and MCP. All of this has to be measured differently: a single run of 30 questions does not notice changes smaller than ~15 percentage points (pp). GraphRAG, a local reranker and query expander, swarms of subagents and a local LLM as the main agent should be rejected on purpose: for 50k notes on an M1 they do not pay off.

## Seventeen changes, ordered by payoff per unit of effort

Impact is estimated against three classes of failure that Knotes already sees in its own runs. The first is queries "in other words" (0/9). The second is overview questions that eat 9–28 calls and break off at the first plausible note or replace data with an estimate. The third is a missed contradiction between two notes. Cost, plan limits and trust are added to this. Effort is estimated relative to the existing code. SQLite already stores frontmatter properties (ADR 0003), the `knotes-tools` layer is shared by the chat and MCP, and an offline search benchmark and a run through the model already exist. Knotes already does a lot at the leaders' level. Block-level search with a cascade of fallback steps is more detailed than the file tools of Copilot V4, which work without an index ([Copilot docs](https://github.com/logancyang/obsidian-copilot/blob/master/docs/vault-search-and-indexing.md)). Pagination, `list_tasks`, `related` and conversation compaction at 90% of the window, modeled on Codex, are also already in place. So the recommendations below add to a strong base rather than replace a weak one.

Separately, a word on what not to do. GraphRAG falls behind plain RAG on single-hop factual questions, and these are exactly what dominates in notes. Besides, it needs a model to extract entities from the whole corpus ([Han et al.](https://arxiv.org/abs/2502.11371)), which means sending the entire vault to the cloud through the plan quota. Knotes already has a free graph built from wiki links and tags. The full qmd pipeline with three local models weighs **≈2.0 GB** ([qmd](https://github.com/tobi/qmd)), several times the budget. Jina v5 is strong but has a **CC-BY-NC** license ([Jina](https://jina.ai/en-US/models/jina-embeddings-v5-text-small/)). OpenAI's `text-embedding-3-small` scores **80.60** on Ukrainian MTEB retrieval versus 92–98 for open models ([DOU](https://dou.ua/goto/Crco)), and it requires sending the vault outside. Subagents spend **~15× the tokens** of a regular chat ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). Apple's on-device model has a context of **4,096 tokens for input and output combined** ([WWDC26](https://developer.apple.com/videos/play/wwdc2026/8121/)), and gpt-oss-20b needs 16 GB of memory ([Hugging Face](https://huggingface.co/openai/gpt-oss-20b)). Neither of them fits the role of the main agent on an M1.

### Thirty questions only notice a fifteen-point change

Measurement comes first, because it decides whether all the following changes can be trusted. With a binomial estimate at n=30 and p≈0.8, the standard error is ≈0.073, so the 95% confidence interval is **±14 pp**. Even a paired comparison of two configurations on the same questions, with 5 runs each, only notices a change of ~15 pp or more. To see 10 pp with confidence, you need about 70 questions (our own calculation using Anthropic's method: SEM, paired differences, several samples per question ([Anthropic](https://www.anthropic.com/research/statistical-approach-to-model-evals))). ADR 0027 itself records that "one run does not distinguish 5–10%". So the difference between 28 and 29 correct answers is noise. Current practice is 20–50 tasks taken from real failures. Each task is run several times, and both pass@k and pass^k are counted. The second metric reflects the consistency the user feels, because 75% on a single run gives only ~42% for three runs in a row ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). OpenAI's hosted graders are no longer supported ([OpenAI](https://developers.openai.com/api/docs/guides/graders)), so the grader has to be local code on top of the same Responses API.

The concrete scheme is as follows. For each question, a golden file stores the expected notes, 2–5 required facts, known wrong "trap" answers and a reference answer. First, Rust checks for free whether the agent opened the expected notes: this is ID-based context precision and recall from RAGAS ([RAGAS](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/)). This check separates a retrieval failure from a generation failure. Next, it checks that link targets exist and counts calls, tokens and the cache share. Then an LLM judge works through a rubric. Each required fact gets a "confirmed / partial / missing" score, and faithfulness is scored separately: the share of claims that rest on tool results the agent actually saw ([RAGAS](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)). The judge is calibrated once on the manual checks that already exist, until its agreement with a human reaches **80%**, the level of agreement between humans in MT-Bench ([Zheng et al.](https://arxiv.org/abs/2306.05685)). The set should include questions whose correct answer is "not found", a question about an excluded note, and hostile notes. The deterministic search benchmark stays as the gate in `cargo test`, and the end-to-end run produces a report with a confidence interval and runs nightly or on demand. The "by meaning" set of 9 queries is too small to accept embeddings. It should be extended to 40–60 queries: a golden set generated by an LLM cost the author of the Ukrainian benchmark less than $0.50 ([DOU](https://dou.ua/goto/Crco)).

## Zero out of nine: lexical search has run its course

### Every serious harness keeps a semantic layer

The most complete local pipeline of 2026 is Tobi Lütke's qmd. It stores an FTS5 (BM25) table and sqlite-vec vectors in a single SQLite file, with EmbeddingGemma-300M by default. Results are fused via RRF with **k=60**, where the original query gets **double weight**, and first place in any list gets a **+0.05** bonus (places 2–3 get +0.02). After that, Qwen3-Reranker-0.6B reranks the top 30 candidates with position-aware blending: at the top positions the reranker is trusted only 25% ([qmd](https://github.com/tobi/qmd)). Basic Memory makes do with a simpler formula, `max + 0.3·min` of normalized scores, keeps the reranker off and uses the English-only bge-small-en ([Basic Memory](https://github.com/basicmachines-co/basic-memory/blob/main/docs/semantic-search.md)). Obsidian Copilot V4 dropped its own index: ordinary file tools find exact matches, and a separate local service, Miyo, finds meaning ([Copilot docs](https://github.com/logancyang/obsidian-copilot/blob/master/docs/vault-search-and-indexing.md)). Smart Connections shows the opposite failure of purely semantic search: its README warns outright that a note containing the exact text of the query may not make it into the results ([Smart Connections](https://github.com/brianpetro/obsidian-smart-connections)). They all reach the same conclusion: both layers are needed.

The argument "agentic grep beats embeddings" came from code. Claude Code dropped its vector index because the index lags behind file changes and raises security questions about where it is stored ([Latent Space](https://www.latent.space/p/claude-code)). For Knotes both objections are weak: the index is local, FTS5 already updates when a file changes, and only changed blocks need rebuilding. Notes are prose with a constant mismatch of words, and in Knotes they are also bilingual. That is exactly where semantics helps the most: even in code, Cursor got a gain of **6.5% to 23.5%** depending on the model, the largest on natural-language queries ([Cursor](https://cursor.com/blog/semsearch)).

### EmbeddingGemma fits the budget, Qwen3 does not

EmbeddingGemma-300M has 308M parameters, supports over 100 languages and takes **<200 MB of RAM** when quantized ([Google](https://developers.googleblog.com/en/introducing-embeddinggemma/)). On MTEB Multilingual it scores 61.15 at 768 dimensions, **59.68 at 256** and 60.62 with Q4_0 quantization ([model card](https://huggingface.co/google/embeddinggemma-300m)). EmbeddingGemma 2 (October 2026, Apache 2.0) has a 270M-parameter text part, an 8,192-token context and 60.41 at 256 dimensions. Its card advises avoiding float16 because of NaN and using bf16 ([model card](https://huggingface.co/google/embeddinggemma-2)). Qwen3-Embedding-0.6B is stronger (MMTEB 64.33 ([card](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B))), but it is twice as large, and in Q8 it does not fit in memory next to the app if kept loaded all the time. There is little data specifically on Ukrainian. The DOU author filtered MTEB down to Ukrainian retrieval: Qwen3-8B scores 98.45, multilingual-e5-large 93.73, bge-m3 92.40, te3-small 80.60. On a legal corpus of 203 queries, MTEB overrated bge-m3: it promised +12 points, but the real gain was +3 ([DOU](https://dou.ua/goto/Crco)). EmbeddingGemma and Qwen3-0.6B were not tested there, so Knotes has to pick the model on its own queries, not by the leaderboard. Frankly, this is the biggest uncertainty in the whole plan.

The memory math is simple. 200k blocks × 256 dimensions in int8 give **~51 MB**, while 768 dimensions in f16 give 307 MB, which is beyond the budget. int8 quantization keeps ~97% of float32 quality without rescoring and ~99% with it ([Hugging Face](https://huggingface.co/blog/embedding-quantization)). At this size an ANN index is not needed. Even sqlite-vec, searching from disk, scans 100k vectors of up to 1024 dimensions in **<75 ms**, and its ANN features are still in alpha ([sqlite-vec](https://alexgarcia.xyz/blog/2024/sqlite-vec-stable-release/index.html), [releases](https://github.com/asg017/sqlite-vec/releases)). A contiguous int8 array in memory with a NEON dot product is simpler and, by our estimate, takes single-digit milliseconds. Freshness is handled the way Basic Memory does it: a SHA-256 hash per chunk, and re-embedding only the changed chunks ([Basic Memory](https://github.com/basicmachines-co/basic-memory/blob/main/docs/semantic-search.md)). FTS5 covers the gap while the vectors catch up. The model should stay in memory only during indexing and per query, and be unloaded after idle time: qmd recreates its contexts after 5 minutes of inactivity at a cost of ~1 s ([qmd](https://github.com/tobi/qmd)). By rough estimate, the initial indexing of 50k notes is 60–120M tokens, which means from several hours to a day on an M1. So it has to be a background job that can resume after a break. Nobody has published throughput numbers for a base M1, so the runtime (llama.cpp as in qmd, Core ML or MLX) has to be chosen with a spike and a measurement.

### Fusion must protect the 0.97, not just lift the 0

The main risk of a hybrid is making keyword queries worse, and they are already nearly perfect. qmd's rule "original ×2 plus a bonus for first place" and its trust in the reranker only in the lower part of the list encode one lesson: a strong exact match must not drown in semantic noise ([qmd](https://github.com/tobi/qmd)). This leads to an important architectural conclusion for Knotes. Semantics cannot be added as one more fallback step at the end of the cascade. The cascade only fires when too little is found, and on a "by meaning" query lexical search often returns enough irrelevant matches that the fallback steps never run at all. Vectors have to run in parallel with block-level FTS5 and always be fused with it. A good start is RRF (k=60) plus a bonus for the top lexical place. With 46 labeled queries, you can move to a convex combination of normalized scores: it outperforms RRF both in-domain and out-of-domain, and its single weight is tuned on a small set of examples ([Bruch et al.](https://arxiv.org/abs/2210.11934)). Results should be tagged with their source (`via: meaning`), so the model knows that a semantic match has to be read before it is cited. Then a separate `semantic_search` tool is not needed, and the tool overlap that Anthropic warns against goes away ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

Block contextualization is almost free. EmbeddingGemma was trained with a `title:` field in the document prompt ([card](https://huggingface.co/google/embeddinggemma-300m)), so "note title › H1 › H2" should go there. Without prompt prefixes, Recall@5 in a small test dropped by 2.8–5 points ([regolo.ai](https://regolo.ai/embeddinggemma-2-vs-qwen3-embedding-benchmarks.md)). A placebo-controlled study from October 2026 showed a small but significant gain from real heading paths and structure-aligned chunks: +0.010…0.022 cov-nDCG@10. Cutting at section boundaries turned out to matter more than adding text ([Kuehlkamp et al.](https://arxiv.org/abs/2610.10170)). Anthropic's contextual retrieval gives more: **−35%** retrieval failures with contextual embeddings, −49% together with BM25 and −67% with a reranker ([Anthropic](https://www.anthropic.com/engineering/contextual-retrieval)). But it requires an LLM call per block, which means tens of millions of tokens of quota and sending the whole vault to the cloud. For Knotes this is unacceptable, except perhaps selectively for PDFs without structure. A local reranker is also unnecessary: the chat model reads and filters the results anyway, and a Ukrainian practitioner was able to turn the reranker off as soon as they switched to a strong embedding model ([DOU](https://dou.ua/goto/Crco)).

### Before vectors: Snowball and queries in two languages

Snowball **3.2.0 (October 17, 2026)** got an official Ukrainian stemmer ([Snowball NEWS](https://raw.githubusercontent.com/snowballstem/snowball/master/NEWS)). It is built on the Russian one and strips adverbial participles, reflexive endings, adjective, verb and noun endings, and -ість. Its limits are known too: fleeting vowels and suppletive forms are handled only as exceptions, and the apostrophe has to be normalized beforehand ([algorithm](https://snowballstem.org/algorithms/ukrainian/stemmer.html)). The Rust crate `snowball_stemmers_rs` supports Ukrainian ([docs.rs](https://docs.rs/crate/snowball_stemmers_rs/latest)). It replaces the current rule of "drop two characters from Cyrillic words of six letters or more". The language of a word can be detected with a cheap heuristic: і/ї/є/ґ mean Ukrainian, ы/э/ё/ъ mean Russian, and otherwise the vault language is used. The unstemmed column has to stay, so that an exact match ranks first. The stemmer will not fix synonyms or cross-language queries. But a study of 11 query expansion techniques found a clear pattern: the weaker the retriever, the more expansion helps it ([Weller et al.](https://arxiv.org/abs/2309.08541)). BM25 facing synonyms is exactly such a weak case. So while there are no vectors, the prompt should get a rule: search for each concept in Ukrainian and English with one or two synonyms ("страховка авто OR car insurance"). Once embeddings arrive, this rule should be relaxed, so it does not dilute a strong query.

## The agent lacks listings and a definition of "done", not steps

### One structured call answers an overview question

The 16-step limit is generous: Obsidian Copilot lets you set 4 to 8 iterations ([newreleases.io](https://newreleases.io/project/github/logancyang/obsidian-copilot/release/3.0.0)). Capacities has a single tool loop, with a lightweight classifier in front of it that cuts unneeded tools, and a shared budget. When the budget runs out, the system returns a **partial answer** instead of breaking off. Merging over 13 client tools into 4 entry points kept tool selection accurate even on cheap models ([Capacities](https://capacities.io/blog/ai-systems-at-capacities)). Knotes' own experience confirms this direction. After `list_tasks` appeared, the question "what is left to do" takes one call and 16 s instead of 23–28 calls and ~55 s. Still, the answer missed plans written as plain text. So the most expensive questions need new listing tools, not a longer loop.

A vocabulary for Obsidian-compatible queries already exists: Bases. These are YAML filters with `and/or/not`, the properties `file.mtime`, `file.tags`, `file.inFolder()`, and dates like `file.mtime > now() - "1 week"` ([Obsidian Bases](https://obsidian.md/help/bases/syntax)). MCP servers expose such queries not as a query language but as a JSON filter tree: JSONLogic in cyanheads ([obsidian-mcp-server](https://github.com/cyanheads/obsidian-mcp-server)), `filters` and `fields` in Basic Memory, where `bm_schema infer` suggests fields based on existing notes ([Basic Memory MCP](https://docs.basicmemory.com/raw/reference/mcp-tools-reference.md)). Hence the recommendation for Knotes: `query_notes`. As input it takes strict JSON with a `where` tree over folder, tag, link, `property.<name>` (the type comes from the index), `mtime`/`ctime` and relative dates (`"today+30d"`), plus `fields`, `sort`, `group_by`, aggregates and pagination. As output it returns `total` and rows with the title, path, requested fields and a one-line snippet. Next to it, a property catalog is needed, with names, types, counts and sample values, so the model finds `expires`, `valid_until` or `термін` ("deadline") before it queries. `list_tasks` should parse Dataview dates `[due:: …]` and the emoji `🗓️ ⏳ 🛫 ✅ ➕` ([Dataview](https://blacksmithgu.github.io/obsidian-dataview/annotation/metadata-tasks/)) and filter by `overdue` and `due_before`. Copilot parses relative dates with a separate `getTimeRangeMs` tool, which the model calls before searching ([TimeTools.ts](https://raw.githubusercontent.com/logancyang/obsidian-copilot/master/src/tools/TimeTools.ts)). In Knotes it is cheaper to accept `since/until` ("7d", "today-30d") directly in `search`, `list_notes`, `list_tasks` and `query_notes` and parse them in Rust, without an extra model step. A `recent_activity` tool covers the question "what did I work on last week" and plans written in prose. Even with a few new tools there will be 12–14 of them, which is below OpenAI's soft limit of 20 functions ([OpenAI](https://developers.openai.com/api/docs/guides/function-calling)). This matters because `tool_search` is not available on the Sign in with ChatGPT route.

### Tools should suggest what to do next

The model stops early partly because it cannot see how much is left. Anthropic advises pagination, filters and truncation with sensible defaults, and, when truncating, a hint on how to narrow the query. Opaque errors should be replaced with concrete advice. A `response_format` parameter (concise or detailed) cut a response from **206 to 72 tokens** ([Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents)). The MCP 2025-11-25 specification moved input validation errors to `isError: true` with "actionable feedback the model can use to correct itself and retry". In its example, a date error includes the current date ([MCP spec](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)). Basic Memory adds a `try_instead` field to errors, and `total` and `has_more` to listings ([Basic Memory MCP](https://docs.basicmemory.com/raw/reference/mcp-tools-reference.md)). For Knotes this leads to three concrete steps. First: an empty or thin `search` should return a hint ("try `list_notes` in folder X" or "the `expires` property exists in 14 notes"). Second: `total` is needed in `search` too, which now returns only `next_offset`. Third: it is worth switching to `strict: true`. The request currently has `strict: false`, and OpenAI advises always using strict mode: `additionalProperties: false`, optional fields as `null` ([OpenAI](https://developers.openai.com/api/docs/guides/function-calling)).

### The prompt should define completeness, primary data and contradictions

OpenAI's guidance for GPT-5.5 replaces a generic "be thorough" with explicit contracts. A search budget is a stopping rule. Searching again is appropriate when the user asks for an exhaustive enumeration, a comparison or a complete list. Minimizing the number of loops must not outweigh correctness. And **"absence of evidence should not automatically become a factual 'no'"** ([OpenAI](https://developers.openai.com/api/docs/guides/prompt-guidance?model=gpt-5.5)). Anthropic advises letting the model say "I don't know", having it first write out verbatim quotes, and then checking each claim against a quote and removing anything unsupported ([Anthropic](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-hallucinations)). Hence a "completeness contract" for Knotes. For "all / what is left / which / how many" questions, the answer must come from a listing tool with a total count, not from a single note. The model reports whether the list is complete and never estimates a count. Numbers, dates and statuses are quoted from a note read in this turn, with a link, and if they are not found, the model says where it looked.

A missed contradiction is a known weakness of models. On WikiContradict, all models do poorly at conveying conflicting sources, especially when the conflict is implicit ([WikiContradict](https://arxiv.org/html/2406.13805v1)). At the same time, explicitly asking the model to reason about a possible conflict in the retrieved documents **"significantly improves"** the answers ([Cattan et al.](https://arxiv.org/pdf/2506.08500)). So the rule must be explicit: if two notes give different values for the same fact, show both with links and dates. For this the model has to see dates, so `mtime` (or the date from frontmatter) has to be returned in `search` and `read_note`, not only in `list_notes`. When the step budget runs out, it is better to return a marked partial answer, as Capacities does, than to allow a silent estimate.

Reasoning effort is another cheap lever. OpenAI advises `low` for "tool use, planning, search" and `medium` for agentic research, and warns that a higher effort can cause "unnecessary searching" ([OpenAI reasoning](https://developers.openai.com/api/docs/guides/reasoning)). Knotes currently does not set `reasoning.effort` and gets the default `medium`. It is worth measuring `low` on lookup questions. The effort should be chosen by a heuristic in Rust, based on words like "усі" ("all"), "скільки" ("how many") and "що лишилося" ("what is left"), on the first turn of the conversation, because changing the effort mid-conversation resets the cache (see below). A "Deep" mode in the UI can raise the effort and the budget, like Deep Research in NotebookLM or the research mode in Khoj. The latter raised accuracy on FRAMES from **42.0% to 63.5%** at the cost of longer runs ([Khoj](https://blog.khoj.dev/posts/evaluate-khoj-quality/)). Subagents gave Anthropic **+90.2%** on research tasks, but they cost ~15× the tokens, so they are used only for parallel, independent subtasks ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). For Knotes, with a plan quota, this is a second tier. If it is ever needed, the best fit is a map-reduce scheme over notes with bounded output, which also limits the damage a poisoned note can do.

### One line in instructions resets the OpenAI cache

The OpenAI cache only works on a byte-identical prefix. It is reset by changes to the tools, `reasoning.effort` or `parallel_tool_calls`, by any editing or truncation of earlier messages, and by dynamic content placed before static content. A cached read costs **0.1× the input price**, and a cache write on GPT-5.6+ costs 1.25× ([OpenAI caching](https://developers.openai.com/api/docs/guides/prompt-caching)). In the plan credits table, cached input for GPT-6.1 Terra costs 1.25 versus 25 per million, which is **1/20** ([ChatGPT pricing](https://learn.chatgpt.com/docs/pricing)). And a Plus user shares one five-hour window across all connected apps ([WorkOS](https://workos.com/blog/sign-in-with-chatgpt-plan-usage-scope)). So every reset cache costs not only money and latency but also quota the user could have spent on ChatGPT itself or on Codex.

Now to the Knotes code. In `lib/knotes-chat/src/chat.rs`, the `instructions` field is built from the constant `INSTRUCTIONS`, the line `Today is <date> (UTC)` and `tools.overview()`. The vault overview is recomputed at most once every 10 s. It contains the exact number of notes and PDFs, the number of files in each top-level folder and the usage counts of the 15 most frequent tags. Since `instructions` comes before the entire `input`, every new note or tag created mid-conversation breaks the cached prefix right after the static text. The next request then reprocesses the whole conversation history at full price, and in a notes app, writing and asking at the same time is normal. The fix is cheap: compute the date and the overview once at the start of the conversation, store them with the conversation as the first developer message, and refresh them only on compaction. While at it, it is worth giving the local date with the weekday and time zone instead of UTC: between midnight and two or three a.m. Kyiv time, UTC still shows the previous day.

The second leak is in `context.rs`. Tool results older than the last two turns are trimmed to 1,500 characters, and reasoning is sent only from the current turn. With every new question the boundary shifts, so the history is rewritten and the cache covers only the part before the first changed item. Rough arithmetic based on the plan table: 10k tokens of an old result in the cache cost about as much as ~0.5k fresh tokens. A version trimmed to a few hundred tokens is sent fresh, and it forces repeated payment for all the turns after it. So before the compaction threshold, trimming most likely costs more than it saves. Knotes already took the 90% threshold from Codex, and it makes sense to keep the history unchanged right up to that point and trim together with compaction. There is a counterargument: Capacities saw "context rot" on cheap models as the prompt grew ([Capacities](https://capacities.io/blog/ai-systems-at-capacities)). Also, the accounting of cached tokens specifically for Sign in with ChatGPT is not officially confirmed. So the first step is to record `usage.input_tokens_details.cached_tokens`: right now Knotes reads only `input_tokens`. Then compare the cache share on the second and later turns before and after the changes. You should also check whether dropping reasoning from earlier turns does harm: GPT-5.6 uses `reasoning.context: all_turns` by default ([OpenAI reasoning](https://developers.openai.com/api/docs/guides/reasoning)).

## Trust is built locally: citations, boundaries, injections

### Without checking, a quarter of citations do not support their sentence

Independent measurements are sobering. In generative search engines, citations fully supported only **51.5%** of sentences, and only **74.5%** of citations supported their sentence ([Liu et al.](https://arxiv.org/abs/2304.09848)). In ALCE, even the best models on ELI5 lacked full citation support in half of the cases ([Gao et al.](https://arxiv.org/abs/2305.14627)). That is the open web, which is harder than a closed vault, and the data predates 2026. But the conclusion for Knotes is obvious: a wiki link written by the model guarantees nothing. Claude API citations chunk a document into sentences and return `cited_text` with **guaranteed valid pointers** ([Claude docs](https://platform.claude.com/docs/en/build-with-claude/citations)). OpenAI's `file_citation` annotations have no text span ([OpenAI](https://developers.openai.com/api/docs/guides/tools-file-search)). Knotes works with OpenAI and its own tools, so the checking will have to happen on the client. The cheapest option is this: the model adds a short verbatim quote to `[[Нотатка#Розділ]]` ("Note#Section"), and Knotes fuzzy-matches it against the note text or the PDF page and gets a character range for highlighting. Links without a match get marked. Perplexity advises trusting not the URLs the model writes but only the results that search returned ([Perplexity](https://docs.perplexity.ai/docs/cookbook/articles/streaming-citations)). For Knotes this means marking a link to a note that no tool returned in this turn. The UX benchmark is NotebookLM: on hover you see the full quote, and a click opens the source at that quote ([Google](https://support.google.com/notebooklm/answer/16179559?hl=en)). Knotes already opens notes at the section; what is missing is the quote popover and the highlighting. NotebookLM also treats a refusal as a full answer: if the answer is not in the sources, it does not give one ([Google](https://support.google.com/notebooklm/answer/16269187?hl=en)).

### The "not for AI" boundary has to live in Rust, not in the prompt

Obsidian Copilot says outright that the search scope is "a search preference, not an authorization boundary" ([Copilot](https://docs.obsidiancopilot.com/settings/)). Notion relies on access permissions, zero data retention (ZDR) at its providers and contracts that rule out training on customer data, and it has no page-level exclusions ([Notion](https://www.notion.com/help/notion-ai-security-practices)). Knotes owns its tool layer, so it can build a real boundary, and this difference has value. ADR 0004 already decided: "notes or tags can be marked 'exclude from AI'; search tools filter them out". The `knotes-tools` code does not do this yet. The implementation is simple: a list of folders and glob patterns, an `ai: false` flag or a `#private` tag, and Obsidian's ignored paths by default. The filter is applied in every tool, so `search`, `read_note`, `links`, `related`, `list_*` and the vault overview all equally fail to see what is excluded. A link to an excluded note is shown as "[excluded]". Each tool needs a unit test, and the evaluation needs a question about an excluded note with the expected answer "not found". The MCP server must apply the same filter, because external clients are also LLMs that see note contents.

### Injections through notes and MCP

Indirect injection through retrieved documents is risk #1 in OWASP LLM01:2025. The scenarios include poisoning documents for RAG and hidden text that makes the model insert an image link and so leak the conversation ([OWASP](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)). Willison describes the "lethal trifecta": private data, untrusted content and an outbound channel. His conclusion: "in web application security, 95% is a failing grade" ([Simon Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). Knotes has private data, and untrusted content too (web clippings, PDFs, imported notes). So the outbound channel is what has to be controlled. Per ADR 0027, replies render only text formatting, and web links open only on click, so remote images are not loaded. This has to be kept on purpose, and when image rendering appears in the chat, remote images must not be loaded. Tool results should be wrapped in marked blocks like `<note path=… untrusted>`, and the instructions should state plainly that note text is data, not commands. The evaluation should get 3–5 hostile notes: "ignore previous instructions", a hidden HTML comment, Base64. For future writing, a principle from the paper on defense patterns fits: once an agent has read untrusted input, that input must not be able to trigger any consequential action ([Beurer-Kellner et al.](https://arxiv.org/abs/2506.08837)). Hence "plan, then execute", or confirmation by default. For MCP, stdio is the right choice: local servers SHOULD use stdio, and HTTP only with a token or over a Unix socket ([MCP security](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)). Write tools should go into a separate scope. From the new specification it is cheap to take `outputSchema` with `structuredContent` (duplicating the JSON in the text) and the `lastModified` annotation ([MCP spec](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)).

### Memory is a note the user can see

All the major assistants have arrived at two layers: a small, editable store of stable facts that is kept in context, and on-demand search over past conversations. In Claude, memory consists of separate topics, has a separate space for each project and by default does not store health, religion or ID document numbers ([Claude help](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context.md)). In Notion it is an "About page" plus a Memories database, both visible and editable ([Notion](https://www.notion.com/help/view-your-notion-agent-memories)). Basic Memory says plainly: "the notes are the memory", and the user reviews every change the agent makes ([Basic Memory](https://docs.basicmemory.com/)). Letta MemFS keeps memory in Markdown under git ([Letta](https://docs.letta.com/letta-code/memory)). Claude's memory tool works on the client: the model asks the app to edit files ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)). For Knotes, the lightest first step is a "Про мене.md" note with the reply language, style, date format and key people. It should go into the same prefix that is frozen for the conversation, so it does not reset the cache. Knotes already resolves aliases of people and places through `aliases`, and, according to the research, none of the products has an explicit glossary. Automatic writing to memory should wait until the writing stage. Then Knotes can offer what competitors lack: both Anthropic and OpenAI admit that deleting a conversation does not delete the memories derived from it ([OpenAI help](https://help.openai.com/en/articles/8590148-memory-in-chatgpt), wording taken from a search summary). A `source: [[Розмови/…]]` ("Conversations/…") link in each entry would make the provenance transparent. Conversations are already stored locally, so a `search_conversations` tool on the same FTS5 costs little.

## Chat and writing: take the best from Copilot, Craft and Apple

### Context and actions on the reply

Copilot V4 has settled on a reference pattern: chips above the input field show exactly what will go with the next message. The active note is attached automatically and can be removed, and a selection becomes a separate chip with its source. `[[` and `@` add notes and folders, and a folder is a scope for the agent to explore, not content inserted whole. The active note is taken at the moment of sending ([Copilot](https://docs.obsidiancopilot.com/context-and-mentions/)). Knotes already has a chip for the open document. The cheapest additions are a selection chip with a line range or heading path on Cmd+L, and an `@`/`[[` picker built on the existing title search, with folders and tags as scope hints for the tools. The set of actions on a reply is almost the same everywhere: copy, insert or replace at the cursor, regenerate. Copilot also automatically saves each conversation as Markdown in the vault ([Copilot](https://docs.obsidiancopilot.com/chat-interface/)). For Knotes these are deterministic local actions that need no write tools: copy Markdown, insert into the active tab, create a note from the reply, save the conversation as a note in a folder excluded from search. Otherwise saved chats will clutter FTS. None of the competitors reviewed documents an "add to daily note" button, so it could become a differentiator. Tool lines should be collapsed into one activity line ("search ×3, read 5 notes, 4 s"), as in Copilot V4. The same version also added editing a sent message and "continue from here in a new conversation" in place of regeneration ([Copilot](https://docs.obsidiancopilot.com/agent-mode-and-tools/)). OpenAI returns short reasoning summaries only on request, via `reasoning.summary` ([OpenAI](https://developers.openai.com/api/docs/guides/reasoning)). They could fill the "Thinking…" line, but whether they are available on the Sign in with ChatGPT route has not been checked. A panel of similar notes that follows the active note, as in Smart Connections ([Smart Connections](https://github.com/brianpetro/obsidian-smart-connections)), will become an almost free by-product of the vectors.

### Writing: proposal, hunk-by-hunk review, commit

There are two families of approaches. Smart Composer proposes an edit, and a second model call rewrites **the whole file**. Review goes block by block in merge style, but, judging by the code, nothing checks at write time whether the file has changed in the meantime ([apply.ts](https://github.com/glowingjade/obsidian-smart-composer/blob/main/src/utils/chat/apply.ts)). Copilot V4 applies first and then shows a "Files changed" card with per-hunk revert. Revert becomes unavailable as soon as anyone edits that fragment ([Copilot](https://docs.obsidiancopilot.com/agent-mode-and-tools/)). Craft undoes the assistant's whole action with a single ⌘Z ([Craft](https://support.craft.do/en/ai-assistant/editing.md)). Notion has "always ask / review for me / no confirmations" modes ([Notion](https://www.notion.com/help/choose-how-notion-agent-asks-for-your-approval)). The Cursor forum has threads demanding the return of per-change review, but the evidence here is only the thread titles, not measured dissatisfaction ([Cursor forum](https://forum.cursor.com/t/bring-back-per-change-apply-inline-diff-review-you-re-throwing-away-your-best-ux-advantage/160856)). Claude Code stresses that checkpoints do not replace version control ([Claude Code](https://code.claude.com/docs/en/checkpointing)). The Knotes plan (git, and a diff with confirmation) matches the best hybrid scheme. Three things are worth refining. First: the write tool accepts patches anchored to a heading path and the expected old text, instead of rewriting the whole file. Second: on acceptance the old text is checked again, and on a mismatch the hunk is marked stale instead of being silently overwritten. Third: each accepted action is one commit named after the conversation and one ⌘Z step. Custom commands can become the first write path. Copilot stores them as Markdown files in the vault, with `{}` variables for the selection and `{activeNote}`, and shows "Replace selection" only when the original text is still in place ([Copilot](https://docs.obsidiancopilot.com/custom-commands/)). Such an insertion is started by the user, goes through the normal undo stack and does not need the diff stage.

### Writing Tools may already work, and may break the markup

Apple documents that `NSTextView` gets Writing Tools automatically ([Apple](https://developer.apple.com/documentation/appkit/enhancing-your-custom-text-engine-with-writing-tools.md)). The Knotes editor is an `NSTextView` on TextKit 2 (ADR 0012), so rewriting, proofreading and summarizing are probably already available, at no OpenAI cost. The catch is hidden markup. Knotes hides markup characters with attributes (a near-zero font size, a transparent color), but they stay in the text storage, so Writing Tools can rewrite or lose `**`, `[[` and table rows. Ulysses, a native Markdown editor for the Mac, keeps links and images on replacement but **ignores code blocks and tables** ([Ulysses](https://help.ulysses.app/dive-into-editing/writing-tools)). So a short spike is needed to check how Markdown survives a replacement. If needed, Knotes can use its own coordinator: the classes for it are in objc2-app-kit ([docs.rs](https://docs.rs/objc2-app-kit/0.3.2/objc2_app_kit/struct.NSWritingToolsCoordinatorContext.html)). On-device voice notes via `SpeechAnalyzer` ([WWDC25](https://developer.apple.com/videos/play/wwdc2025/277/)) have become standard in commercial apps, but for a personal vault they are a low priority.

## Conclusion

The map of changes shows two things that are not visible from the individual recommendations. First: in 2026, a notes harness gets its edge not from the model but from what it gives the model. That means narrow tools that return listings with totals, contracts for "what counts as done", and a prefix that stays stable for the cache. All of this is fully in Knotes' hands and costs almost nothing. Second: Knotes' local architecture turns the leaders' main objections into advantages. Claude Code dropped embeddings because the index goes stale and raises privacy concerns, while in Knotes the index is local and fresh anyway. Copilot cannot make its privacy boundary real because it does not own the tools, and Knotes does. Neither advantage is realized yet: the "not for AI" boundary exists only on paper, and there is no semantic layer.

Hence the order of work. First, fix measurement and the cache, because without them you cannot see whether the rest helps, and the plan quota is already leaking. Next, the prompt, the listing tools and Snowball, which cover overview questions and part of the word forms. Then embeddings, with an acceptance test on the extended set of "by meaning" queries and the condition of not degrading the 0.97 on keyword queries. Only after that, writing. Three things remain uncertain and have to be measured, not guessed: the quality of EmbeddingGemma and Qwen3-0.6B specifically on Ukrainian notes (no published data exists), embedding throughput on a base M1, and whether the Sign in with ChatGPT plan really charges less for cached tokens.
